    How a run works

    Pressing Run sends the code in the editor to the playground Worker, which streams each step back to the panel as it happens.

    1. Resolve dependencies

      The [dependencies] in the --- block at the top of the snippet are resolved against the crates.io index the way Cargo does it: semver ranges, features, optional and renamed dependencies, and per-target dependencies. The versions picked are kept in Workers Cache for ten minutes.

    2. Build every crate in Workers

      Each crate is compiled by rustc in the Compiler Worker, several at a time, and kept in R2 under a hash of its source, features and dependencies, with Workers Cache in front. A build script is compiled into a program and run in a Dynamic Worker with Cargo’s environment; when it runs rustc --version, that call goes back to the Compiler Worker. Once every crate a snippet needs is built, they’re kept together, so the next run gets them in one lookup.

    3. Run proc macros in their own sandboxes

      rustc can’t load a proc macro as a shared library here, so each proc-macro crate becomes a WebAssembly module of its own. To expand #[derive(Serialize)], rustc pauses (JSPI), the macro runs in its module’s Dynamic Worker with no network, and the macro’s questions about the code come back to rustc over RPC.

    4. Compile and link the snippet

      rustc 1.98.1 itself, compiled to wasm32-unknown-emscripten as 53 MiB of WebAssembly, compiles the snippet. On its own, a snippet links with wasm-ld inside rustc; with crates, the Linker Worker links it, so the crates’ object code never has to fit in the compiler’s memory. A snippet built the same way before comes from the cache; change anything and it compiles again.

    5. Run it in a sandbox

      The program runs in a fresh Dynamic Worker with no network access, on a shared Emscripten runtime. Standard input, arguments, exit codes and panics behave as they do natively. It runs every time, even when its build came from the cache.

    Built on the Workers platform

    Nothing here runs outside Cloudflare. Each part of a compiler toolchain maps onto a Workers product.

    Rust on the Emscripten targetwasm32-unknown-emscripten
    rustc, its linker, and every program it builds are compiled for the Emscripten target, the target Rust Workers build on. A program gets a real libc, a filesystem, stdin and stdout, panics that unwind, and exit codes, without WASI.
    Dynamic Workersworker_loaders
    Every program, every build script and every proc macro runs in an isolate created on demand from the code that was just compiled, with globalOutbound: null, so untrusted code from crates.io never touches the network.
    Service bindings and RPCservices, WorkerEntrypoint
    The playground, the compiler and the linker are separate Workers, each with its own memory. They call each other over RPC, including callbacks: a proc macro’s questions about the code flow back into the rustc that’s waiting on it.
    Workers Cachecache, exports
    In front of R2, close to whoever pressed Run: resolved versions, compiled crates, all of a snippet’s dependencies in one response, and the snippet’s own build. Hits come back without running any code.
    R2r2_buckets
    The crates.io index, downloaded crates, every compiled crate and every compiled snippet, keyed by a hash of everything that went into it. A crate is compiled once; after that, any snippet that needs it gets it in milliseconds.
    JavaScript Promise IntegrationWebAssembly.Suspending
    rustc is synchronous code, but it can pause mid-compile while a macro runs in another Worker, then pick up where it left off. Programs pause the same way while a child process runs, which is how a build script’s rustc --version reaches the compiler.
    Streaming responsesTransformStream
    The panel above is fed by the run itself: the playground Worker writes each step to the response as it happens, one line of JSON at a time.
    Workers Static Assetsassets
    This page, whose editor is Monaco, the editor inside VS Code. And std’s crate metadata, 75 MiB that doesn’t fit in the compiler’s bundle beside rustc: the compiler’s own assets, as compressed pages that only it reads.

    What it took

    rustc wasn’t written to run on WebAssembly. Putting it on the Emscripten target took seven small patches to the compiler, one to std, and two fixes in the runtime, each small enough to read in one sitting.

    1. rustc 0001Run the compiler without threads on hosts that lack themThe front end runs inline, and codegen waits for its join.
    2. rustc 0002Link with wasm-ld in-process on WebAssembly hostsThere are no processes to spawn a linker in.
    3. rustc 0003Allow wasm-ld as the linker for Emscripten targetsWith the arguments emcc would have passed it.
    4. rustc 0004Build rustc_driver as an rlib tooEmscripten has no shared libraries, so rustc links statically.
    5. rustc 0005Give Emscripten hosts a default sysrootrustc finds its sysroot with dladdr, which isn’t available.
    6. rustc 0006Run proc macros out of process on Emscripten hostsThe bridge protocol is unchanged; only its byte buffers cross over.
    7. rustc 0007Read crate metadata a page at a time on Emscripten hostsMapping a file copies all of it there, and std’s metadata alone is 75 MiB.
    8. stdSpawn processes with posix_spawn on EmscriptenEmscripten has no fork. With the matching libc bindings.
    9. runtimeHand child processes to the host, and let pipes reach EOFThat’s how a build script’s rustc call reaches the compiler Worker.
